#+title: linux-rg literature review

* Scope

This document records research-grade sources used to evaluate kernel choices
across linux-rg machine profiles. It is the shared evidence base. It complements
per-profile patch rationale (e.g. =docs/rgx1gen11-kernel.org=) and candidate
notes in =docs/candidates.org=.

Sources are limited to peer-reviewed venues, IETF drafts, kernel.org and LWN
primary coverage, USENIX/LPC proceedings, and vendor technical documentation.
Downstream patch aggregators are not treated as evidence on their own.

Evidence in this file is evaluated for applicability per profile. A source may
justify a patch for one profile (e.g. hybrid Intel laptop) while being
inconclusive or irrelevant for another (e.g. Zen 5 desktop).

Companion: =docs/candidates.org= (candidates + applicability map) and
per-profile targets/kernel docs.

** Example profile context (rgx1gen11)**

- Intel Core i7-1365U, Raptor Lake-P/U hybrid.
- KIOXIA XG8 NVMe.
- Intel Iris Xe, CNVi Wi-Fi, Thunderbolt 4.

See =docs/rgx1gen11-targets.org= for the full verified inventory. New profiles
(e.g. rgam5terra) document their own context in their targets doc; literature
entries here remain shared unless a profile-specific note says otherwise.

** What OokCite resolves well

Peer-reviewed ACM/USENIX/arXiv DOIs (BBR, BFQ, BBR/IMC, EuroSys scheduler paper,
SWAM, ASA preprint). Crossref-backed metadata includes corrected author lists.

** What often fails (keep URL + venue, no fabricated DOI)

| Source type | Example | OokCite result |
| USENIX ATC full papers | Lebeck ATC 2020, Li KBench ATC 2024 | Often no Crossref DOI; use usenix.org PDF URL |
| HOTSTORAGE workshop | Whitaker ULL NVMe 2023 | Workshop proceedings may not index |
| LPC / Linux Plumbers | sched_ext, MGLRU, hybrid Intel | Slides/PDF only; grade B not A |
| LWN / kernel.org docs | EEVDF, PSI, MGLRU | Primary engineering literature; no DOI |
| Vendor blogs | Meta OOMD, Intel whitepapers | Grade C; reverse_lookup unreliable |

When =reverse_lookup= returns low scores or wrong-domain matches (e.g. nursing
admission spam DOIs), **reject the hit** and keep the PDF URL as evidence.

* Why kernel research feels absent ("why is no one studying this?")

If you tune a desktop kernel from Liquorix threads, CachyOS patches, or Kolivas
mailing-list lore, the honest answer is: **a lot of kernel work is never written
up as citable science**. That is not the same as "no one studies kernels." The
field is split across venues, incentives, and publication cultures that rarely
reach patch READMEs or distro forums.

** Structural reasons academia under-publishes *your* kernel questions

| Factor | Effect |
| Measurement cost | A scheduler or IO scheduler claim needs fixed hardware, kernel ABI, config matrix, thermal state, and workload script. One laptop model is one data point. Reviewers want generalization; practitioners want one box that boots. |
| Incentive mismatch | OS faculty moved toward cloud isolation, eBPF security, ML systems, and hardware-software co-design. "Does BFQ beat none on a ThinkPad NVMe under Sway?" is too specific for SOSP, too applied for theory venues. |
| Mainline as publication | Many "results" land as lkml threads + merge commits. EEVDF shipped in Linux 6.6 with LWN coverage, not an ACM proceedings paper. The *artifact* is the patch, not a PDF. |
| Industry owns production tuning | Meta (PSI, OOMD), Google (MGLRU path, Android binder Rust), Intel (hybrid scheduling LPC), and cloud vendors publish blogs and LPC slides. Peer review is optional when billions of machines run your code. |
| Downstream patch desert | BORE, Liquorix zen cuts, Cachy CONFIG_CACHY hunks, and ADIOS ship as git series with Phoronix posts, not controlled studies. Users confuse *availability* with *evidence*. |
| Negative results vanish | "mq-deadline did nothing on ULL NVMe" (HOTSTORAGE 2023) is valuable. Few academics publish "we tried ten schedulers on a laptop and nothing helped." |
| Reproducibility debt | Kernel + firmware + ACPI + panel + NVMe APST + iwlwifi power_save = opaque state. Papers that omit this are not reproducible on a second machine. |

** What people mistake for "kernel research"

| You see | What it actually is | Literature grade |
| Phoronix headline "X% faster" | Benchmark journalism; often one kernel build, one machine | C at best |
| Reddit / Discord patch stacks | Engineering folklore; may be correct, unverified | D |
| Distro default config | Accumulated conservatism, not optimization proof | B/C |
| =make -j9= wall time | Build throughput proxy; weak proxy for UI latency | D unless paired with sched/PSI metrics |
| Gaming FPS tests | GPU-bound; tells you little about fair.c sysctl | D for scheduler claims |

** The citation gap linux-rg sits in

Each profile has its own "known evidence desert". For the initial rgx1gen11
profile (2023 ultrabook): mainline Linux 7.0 is post-CFS, post-MGLRU-merge,
mid-sched_ext, on hybrid Intel silicon.

The published literature lags the patch queue by 2-5 years. Distro choices
therefore sit in a known evidence desert:

- Carried fair-class tweaks (BORE, 0010-0013): engineering bets, grade D.
- Carried zen MM/cpufreq cuts (0014-0016): Liquorix folklore, partially upstreamed.
- Literature-backed choices: MGLRU, PSI, BBR family, BFQ *class*, HOTSTORAGE
  skepticism on ULL NVMe defaults, hybrid scheduling *problem statement*.

This repo grades patches A-D and separates *problem framing* (often A) from
*patch implementation* (often D). The same grading applies when evaluating
patches for new profiles (e.g. Zen 5 + discrete GPU).

** What would count as real science for a profile

Minimum bar for promoting any candidate from D to B on a given profile:

1. Fixed hardware + firmware/BIOS documented in the profile's targets.org.
2. Fixed workload scripts defined for that profile.
3. A/B: stock Arch kernel vs linux-rg on the target machine.
4. Profile-appropriate metrics (e.g. for a desktop: build throughput + gaming
   frame time consistency + thermals; for a laptop: s2idle, battery, wakeup).
5. Pre-declared success thresholds in the profile's targets doc.
6. Negative results recorded in =docs/candidates.org= decision gates.

This is reproducible systems measurement, not a paper -- but it is **more honest**
than most patch-stack marketing.

* Evidence grading

| Grade | Meaning | Examples |
| A | Peer-reviewed or standards-track | USENIX, ACM, IMC, PAM, HOTSTORAGE, IETF drafts |
| B | Primary kernel engineering literature | kernel.org docs, LWN, LPC slides with published materials |
| C | Vendor or production engineering reports | Intel, Lenovo, Meta/Facebook engineering notes |

Takeaway: **the kernel is studied heavily for security, cloud scale, and protocol
measurement**. It is **under-studied for "my laptop feels snappier with patch X"**
where X is a downstream fair.c diff. That is the WTF feeling, stated precisely.

* Specialized-workflow kernels

The literature on customizing Linux (or a Linux-shaped host) for a *named
workflow* is large. Almost none of it is a fair.c hunk for a daily-driver
laptop. The transferable result is usually a **userspace controller** or a
**kconfig pin of an existing controller**, not a new in-tree class.

** How the farm grades a specialized-workflow paper**

| Verdict | Meaning | linux-rg action |
| CARRY | Peer-reviewed *and* a mainline or already-carried artifact | Keep the pin or patch |
| PIN-CONFIG | Paper names a mainline knob this repo already (or must) compile | Overlay + check script |
| USERSPACE | Paper's policy lives in a daemon / BPF expert / sessiond leaf | Document; do not write kernel C |
| REJECT | Requires dedicated cores, CXL, DPDK, PREEMPT_RT, or a research OS | Cite; do not enable |

kernel documentation and LWN pre-merge series (Molnar, Gorton, 2023-2024), not a

design rationale as grade B, formal verification as absent.
